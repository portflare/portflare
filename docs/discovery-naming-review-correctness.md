# Discovery Naming Correctness Review

> Status: Implemented. No correctness blockers remain after reviewer fixes.

## Review
- Correct: The implementation preserves the backward-compatible default naming path. `runDaemon` now loads `DiscoverNaming` but `generatedDiscoveryName` falls through to `app-{port}` for the zero/default template, so empty new env vars keep current behavior (`client/cmd/portflare/main.go:277`, `client/cmd/portflare/main.go:1062`, `client/cmd/portflare/main.go:1182`).
- Correct: Exact per-port overrides keep precedence over descriptor/protocol generated names. `discoveryCandidateForPort` checks `ExactNameByPort` before calling `generatedDiscoveryName` (`client/cmd/portflare/main.go:1160`), and `TestDiscoveryNamingExactOverrideWins` covers this (`client/cmd/portflare/main_test.go:124`).
- Correct: Parser validation matches the plan for supported templates and protocol labels. `parseDiscoveryNameTemplate` accepts empty/`port`/`app-port`, `descriptor-port`, `descriptor-proto-port`, and `descriptor-proto`, rejecting unknown values (`client/cmd/portflare/main.go:1308`). `parsePortProtocolMap` slugs labels and rejects missing/invalid ports and empty labels (`client/cmd/portflare/main.go:1396`).
- Correct: Scanner integration threads the typed naming config through discovery. `/proc` candidates are passed to `buildDiscoverCandidates` via `discoverListeningHTTPCandidates(..., naming)` (`client/cmd/portflare/main.go:1083`), and daemon refresh uses `s.cfg.DiscoverNaming` (`client/cmd/portflare/main.go:584`). Local API rescan calls the same `refreshDiscovery`, so it uses daemon config rather than per-request overrides (`client/cmd/portflare/main.go:556`).
- Correct: Docs cover the required UX and risks: examples for descriptor/protocol templates, exact override precedence, protocol-label caveat, and public URL/app identity churn are documented in `client/docs/usage.md:49`, `client/docs/usage.md:64`, `client/docs/usage.md:88`, `client/docs/usage.md:90`, and `client/docs/usage.md:92`; README and learnings also include the protocol-label caveat (`client/README.md:59`, `docs/learnings.md:341`).
- Fixed: I found a collision edge case where generated collision suffixing could create a final name equal to an exact override, e.g. exact `devbox-http-8080` plus generated `devbox-http` for port 8080. That would allow two candidates to share one `AppName` during refresh. I updated `buildDiscoverCandidates` to reserve exact names before assigning generated names and to add deterministic secondary suffixes when needed (`client/cmd/portflare/main.go:1115`). Added `TestDiscoveryNamingGeneratedSuffixAvoidsExactOverride` (`client/cmd/portflare/main_test.go:184`).
- Fixed: I found a parser edge case where duplicate exact-name checking could falsely reject `PORTFLARE_CLIENT_DISCOVER_NAMES=3000=web,3000=api,8080=web` because it remembered overwritten same-port values. I changed `parsePortNameMap` to apply last-write-by-port first, then check duplicate final names across ports (`client/cmd/portflare/main.go:1358`). Added `TestParsePortNameMapAllowsSamePortLastWriteBeforeDuplicateCheck` (`client/cmd/portflare/main_test.go:76`).
- Note: Positive local API rescan coverage remains indirect. The code path is correct (`handleDiscoveryRescan` -> `refreshDiscovery` -> `DiscoverNaming`), and disabled-rescan coverage exists, but there is no focused positive test proving `/discovery/rescan` returns/apply names from a configured daemon because discovery currently reads live `/proc` directly. Consider adding an injectable scanner in the future client refactor to make this behavior directly testable.
